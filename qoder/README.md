# 赛题速查

OceanBase 数据库大赛官方文档的一句话检索工具。队友问「AMD 题仓库地址怎么填」，
以前要翻 6 个网页对三份文档，现在输入一句话，直接拿到原文段落、出处文档和链接。

## 30 秒跑起来

> 依赖装在项目内 `.venv`，以下命令必须用 `.\.venv\Scripts\python.exe`。
> 系统 python 是 MSYS2 3.14，装不上 pylibseekdb。

```bash
# 1. 装依赖（若 .venv 不存在，先 python -m venv .venv）
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

# 2. 建索引（会删掉 data/seekdb.db 整目录后重建，约 5 秒）
#    不要用 TRUNCATE 原地重建：会导致全文索引打分虚高、评测数字变得不可信
.\.venv\Scripts\python.exe -m src.build_index

# 3. 启动 Web 服务（默认端口 8000）
.\.venv\Scripts\python.exe -m src.server
```

浏览器打开 http://127.0.0.1:8000 。命令行检索：`.\.venv\Scripts\python.exe -m src.retriever "问题文本"`。

## 实测数据

| 指标 | 数值 |
| --- | --- |
| 语料 | 抓取 65 篇官方文档，48 篇入库（17 篇是语雀卡片占位页，有效正文不足 120 字被跳过）/ 466 个文本块 / 17 万字 |

| 召回率 | Recall@1 89.3% / Recall@3 92.9% / Recall@5 96.4%（28 题自建评测集） |

28 题里 25 题命中第 1 位、26 题进前 3、27 题进前 5，剩下一题没进前 30。
复现评测：`.\.venv\Scripts\python.exe tools/eval_retrieval.py`。

## 验证样例

前置：已执行 `-m src.build_index`，`/api/stats` 返回 `{"chunks": 466, "notes": 0}`。

### 样例 1：问一条赛题要求，能定位到具体小节

```bash
.\.venv\Scripts\python.exe -m src.retriever "AMD 题提交的仓库地址必须是什么格式"
```

预期第 1 名是《AMD > 四、云端统一评测流程 > 4.1 答题仓库地址格式（必须）》。
实际输出（本轮实测）：

```
routes={'vector': 40, 'fulltext': 40, 'title': 16, 'fused': 78} 别名=['仓库', '提交', '题'] 耗时=164ms
1. AMD > 四、云端统一评测流程 > 4.1 答题仓库地址格式（必须）
2. 比赛仓库地址 >
3. AMD > 四、云端统一评测流程 > 4.1 答题仓库地址格式（必须）
```

`routes` 里的三个数字是三条召回路各自返回的候选数（每路 40 条，标题路按标题命中数）。

### 样例 2：多路命中能看出来是哪条路找到的

```bash
.\.venv\Scripts\python.exe -m src.retriever "什么时候该触发一次记忆处理"
```

预期第 1 名是《赛题七：按新增来源条目数触发记忆处理》。实际：

```
routes={'vector': 40, 'fulltext': 40, 'title': 9, 'fused': 73} 别名=['记忆'] 耗时=108ms
1. 赛题七：按新增来源条目数触发记忆处理 > 一、题目背景
2. 赛题七：按新增来源条目数触发记忆处理 > 二、题目内容 > 2.2 接口与数据
3. 赛题九：来源撤回后的记忆停用与恢复 > 二、题目内容 > 2.1 通用要求与范围
```

同一文档最多出 2 条（`_rank` 里的 `doc_slots` 上限），避免一个文档刷满结果。

### 样例 3：团队记忆召回

```bash
# 记一条（也可在网页上点「记一条」）
.\.venv\Scripts\python.exe -c "from src.retriever import remember; print(remember('wyd','Qoder 题的代码要放哪','放在 powercontext 仓库的 qoder/ 目录','qoder'))"

预期输出末尾出现「记忆 1 条」，内容包含刚写入的答案。实测：

记忆召回条数: 1

```

记忆走的是 `notes` 表上的另一个 FULLTEXT 索引，和文档检索互不干扰。

### 指定技术（seekdb）在哪发挥作用

```bash
.\.venv\Scripts\python.exe tools/inspect_db.py
```

实测输出（节选），三个索引分别对应三条召回路径：

```
表: ['chunks', 'notes', 'search_log']

chunks 的索引:
  - PRIMARY        列 id         类型 BTREE
  - ft_chunk       列 text       类型 FULLTEXT   ← 全文路 MATCH ... AGAINST
  - idx_chunk_emb  列 emb        类型 VECTOR     ← 向量路 ORDER BY l2_distance(...) APPROXIMATE

notes 的索引:
  - ft_note        列 search_text 类型 FULLTEXT  ← 记忆召回

chunks 行数: 466
统计: {'chunks': 466, 'notes': 1, 'search_log': 1}
最近查询:
  - [1] 构建加速比怎么算（2 条 / 72ms）
```

向量列是 `VECTOR(1024)`，建索引用 `WITH (distance=l2, type=hnsw)`；
中文全文必须用 `WITH PARSER ngram`，否则中文检索不出结果。
两路 SQL 分别在 `src/retriever.py` 的 `_vector_route()` 和 `_fulltext_route()`，
`search_log` 表由 `log_search()` 写入，网页上的「最近查询」就读它。

### 完整回归

```bash
.\.venv\Scripts\python.exe tools/eval_retrieval.py
```

28 题逐题打印名次，末尾给 Recall@1/@3/@5 与耗时中位数，未命中的题目会列出来。

## 技术要点

- **原地重建会污染全文索引（踩过的坑）**。`TRUNCATE TABLE` 之后 seekdb 的全文索引
  里并没有清掉倒排条目，原地重建几次后同一个词被重复计入，`MATCH ... AGAINST`
  的打分整体虚高：同一道题在重建过 3 次的库上全文路 top1 是 15.71 分、在干净库上
  只有 3.37 分，名次从第 1 掉到第 5，28 题 R@1 因此从 89.3% 虚涨到 96.4%。
  `OPTIMIZE TABLE` 清不掉。所以 `build_index` 重建时直接删整个库目录
  （`wipe_db_dir()`），评测前也照这个来——不然你会拿到一个漂亮的假数字。
- **三路召回 + RRF 融合**。向量路（HNSW l2）和全文路（ngram MATCH）的分数
  不能直接相加：一路是距离、越小越好，一路是相关度分值、越大越好，量纲不同
  方向相反。RRF 只取名次做倒数融合（1/(60+rank)），避开量纲问题。
- **标题加成算「实义单元覆盖率」，不数全部 n-gram**。一次 14 字的查询会被切成
  23 个 token，其中大半是「每道」「道赛」「题对」这类跨词边界碎片；分母一旦这么算，
  覆盖率对每个候选都接近 0，加成等于没加。改成只数 ASCII 词和「不含功能字的二元组」
  （实义单元），分母才反映查询真正在问什么。
- **按 IDF 挑"关键词"行不通**。直觉上该拿 IDF 最高的词去匹配标题，但本语料里
  IDF 顶格（6.45，df=1）的恰恰是碎片：「维护模」「忆处」「发一」「每道」全是噪音。
  按 IDF 选词会让标题路选出噪声词，覆盖率改成平方放大后可抵消这一点。
- **覆盖率用平方放大，不用线性**。线性加成压不住 RRF 的名次差：问
  「AMD 题提交的仓库地址必须是什么格式」时，正确小节《4.1 答题仓库地址格式》
  覆盖率 0.67，但《比赛仓库地址》那张表在三条路上都靠前、RRF 高 1.55 倍，
  线性加成（×1.20 vs ×1.10）翻不过来；平方后（×2.35 vs ×1.33）才翻得过来。
  干净库上：不加任何加成 R@1 78.6%，只加标题（1.0）85.7%，标题 3.0 + 正文 1.0 得 89.3%。
- **正文覆盖率单独算一项，权重比标题小一个量级**。只看标题会漏掉一类错：
  问「构建加速比怎么算」，《全文索引构建性能优化》正文里「构建」出现 11 次、
  但「加速」「速比」「加速比」各 0 次，靠标题里的「构建」加向量/全文名次排到了第一；
  而《AMD》6.1 节正文「构建」40 次、「加速比」14 次，只能排第三。
  加上正文实义单元覆盖率后 AMD 回到第一。正文比标题容易命中（块长、单元多），
  所以权重取 1.0（标题是 3.0）。这一项对 28 题评测**没有影响**（加不加都是 89.3%），
  它只为「只沾一个词」这类错服务，加它是为了别让裸查询给出一次都没提过的文档。
- **别名扩展要去重**。「题」和「赛题」两个键会同时命中「每道赛题…」，
  把「赛题」在扩展串里追加两次——而它是本语料最通用的词，重复计数等于给它
  加了三倍权重，把判别词（仓库/分支）顶下去。已在 `expand_query` 里按
  「查询里已有就不再加、多个键命中同一个词只加一次」处理。
- **标题加成用原查询词，不用别名扩展词**。别名「构建 → 索引构建」会切出
  索引/引构/索引构，全部落在《全文索引构建性能优化》的标题里，把正确答案
  《AMD / 九、性能计分》顶下去。职责划分：扩展词只用于召回，不用于排序判定。
- **专有名词校验**。RRF 只看排名不看分差，「AMD」这种强区分力词一旦没命中，
  块内容里完全没出现该词的结果要乘 0.4 惩罚，否则排名信息会被抹平。

## 已知限制

28 题里 25 题命中第 1，剩下三个失败案例各自暴露了不同的问题：

- **「每道赛题对应哪个仓库和分支」根本没进前 30**。答案是《比赛仓库地址》，全文只有
  一个 520 字的表格块、没有小节标题，正文是「题目 / 仓库地址 / 分支」加一串 GitHub
  链接。表格里「仓库」「分支」各只出现一次，词频天然拼不过《赛题一：准备 PowerContext
  仓库》这种正文反复提到仓库的文档，三条召回路径都没把它带进候选。为它改评测集或者
  加特例，等于自己骗自己，所以记在这里。
- **「AMD 题对召回率的最低要求是多少」排第 5**。前 3 名都是标题带 AMD 的文档
  （Radeon 使用与部署、部署上报失败修复），「AMD」这个强区分力词把真正回答问题的
  《AMD > 九、性能计分》压下去了。暴露的是词袋检索的固有短板：区分力强的词会盖过
  问题真正的焦点（召回率）。
- **「提测以后多久能出成绩」排第 2**。第 1 是 FAQ 的「Q：提测次数」小节——短、密、
  「提测」命中更直接；而「多久出成绩」这层意思只能靠 `synonyms.json` 里的
  时效/时间/分钟间接表达。别名表覆盖不到的说法就检索不到。
- 向量是词袋特征哈希，没有真正的语义泛化。同义改写全靠 `data/synonyms.json`
  兜底，遇到新说法要往里补。
- 加成权重（标题 3.0 / 正文 1.0 / 幂次 2）是在这 28 题上调出来的：标题 2.0~4.0
  结果都是 89.3%，取了中值；但换语料或换评测集要重新标定，不能当通用常数。

## 目录结构

```
kaoti-sucha/
├── src/
│   ├── text.py         # Markdown 切块、中文分词、blake2b 特征哈希向量化、摘要
│   ├── db.py           # seekdb 嵌入式库封装（三张表 + HNSW 索引）
│   ├── build_index.py  # 建库：切块 → IDF → 向量化 → 批量写入 → 建 HNSW
│   ├── retriever.py    # 三路召回 + RRF 融合 + 标题加成 + 记忆召回
│   └── server.py       # 标准库 http.server Web 服务（4 个 API + 静态页）
├── tools/
│   ├── fetch_docs.py   # 语雀抓取官方文档到 data/docs/ + index.json
│   ├── eval_retrieval.py  # 回归评测，输出 Recall@1/@3/@5 与未命中名次
│   └── inspect_db.py   # 体检库：表、索引类型、行数、最近查询
├── web/
│   └── index.html      # 查询界面：结果卡片、三路命中标签、团队记忆、记一条
├── data/
│   ├── docs/           # 抓取的 65 篇官方文档（markdown）与 index.json
│   ├── idf.json        # 词表 IDF 权重
│   ├── synonyms.json   # 领域别名表（子串匹配做查询扩展）
│   ├── eval_questions.json  # 28 题自建评测集
│   └── seekdb.db/      # 嵌入式数据库（chunks / notes / search_log）
├── requirements.txt    # 依赖：pylibseekdb、pymysql、numpy
└── .gitignore          # 虚拟环境与本地数据库不进仓库，评审按「30 秒跑起来」重建
```
